# Artone v3 — ソクラテス問答による現状評価 (2026-09)

> 手法: **問い → 答え → 反問**。答えるたびに「本当にそう言えるか?」を問い直し、
> 反証できない主張だけを残す。評価軸はマスク流の5段階
> (①要件を疑う ②削除する ③単純化する ④加速する ⑤自動化する) に揃える。
>
> **すべての主張はコード実測に基づく。** 出典のない断定は書かない。
> 測定日: 2026-09-01 / 対象: `main` @ #62 + 本セッションの未出荷分

## 第一問: このプロダクトは「動く」のか?

**答**: 動く。実ブラウザ (Chromium) で組み上がった製品を起動し、コアループ
「取り込む → タイムラインに載る → 選ぶ → プレビューに実映像が出る」が通ることを
確認した。コンソールエラーはゼロ。

**反問: 「動く」と言うが、どうやって確かめたのか? テストが緑なだけではないか?**

以前はまさにそれだった。本セッションで実際に製品を起動するまで、検証は
**すべてモジュール単位**だった。そして起動してみたところ、**製品は動き、E2E
テストのほうが壊れていた** — 23件中16件が失敗。`data-testid` はアプリ側に
1つも存在せず、共同編集パネル・共有リンク・モバイルナビという**実装されていない
画面**を検証していた。さらに「Verify playback state changed」のように
アサーションを1つも持たないテストが素通しで緑になっていた。

> **教訓 (①要件を疑う)**: 「テストが緑」は「製品が動く」の証拠ではない。
> 中身の無いテストは、無いことより悪い — **あるつもりになる**。

現在は E2E がコアループを実際に通し、起動時とループ実行時に**コンソール
エラーが出ないこと**まで検証する (`tests/e2e.spec.ts`)。

## 第二問: 長所は何か?

### 長所1: エンジンが唯一の真実である

タイムラインの状態は `timeline/magnetic-timeline.ts` の `MagneticTimeline` が
単独で持ち、UI (`app/shell.tsx`) は購読して描くだけ。Inspector の表示値も
`toClipSelection()` でエンジンから毎回導出する。

**反問: それは設計の話であって、守られている保証は?**

守られていなかった時期の症状で確かめられる。UI が独自の配列を持っていた頃は
①エンジンの編集ロジックが全て死蔵 ②undo/redo が画面に効かない
③**クラッシュ復旧が空のタイムラインを保存していた**。Inspector が値をコピー
していた頃は、ドラッグ後に別項目を編集すると**古い開始位置が書き戻されて
ドラッグが無言で取り消された**。いずれも回帰テストで固定済み
(`tests/timeline-commands.test.ts` / `tests/inspector-engine-sync.test.ts`)。

### 長所2: 検証できないものを出荷しない規律

「区間書き出しは jsdom で検証できないから実装しない」と判断し、実装を見送った。

**反問: それは規律か、それとも単なる怠慢の言い換えではないか?**

**鋭い。実際そこには誤りがあった。** 「検証できない」という事実認定のほうが
間違っていた — 本リポジトリには Playwright が入っており、コンテナの Chromium は
WebCodecs (VP8/VP9/AV1 の encode/decode) を持つ。検証手段が無かったのではなく、
**単体テストの実行環境に無かっただけ**。判明後ただちに実装し、実ブラウザで
「GOP の途中から始まる区間を切り出して**ちょうど30フレーム**」まで検証した。

> **教訓**: 規律そのものは正しい。ただし「検証できない」は**主張であって前提では
> ない** — 定期的に反証を試みなければ、規律は怠慢の隠れ蓑になる。

### 長所3: 失敗を名指しする

書き出しが素通しで編集を再現できない場合、`export/export-source.ts` は
妨げている要因を**全て列挙**する (`multiple-sources` / `multiple-clips` /
`transformed` / `offset`)。1つ直せば通るという誤解を与えないため。
`renderTimeline()` は音声付き素材を映像だけで書き出すことを拒否していた
(現在は音声を運ぶので解消)。

**反問: 名指しする文言は、実装に追従しているか?**

**追従していなかった。** 連結も合成も実装済みなのに「compositing is not wired
yet」と言い続けていた (PR #60 で修正)。コードは正しく、それを説明する文だけが
古い — 見つけにくく、読んだ人を確実に誤らせる種類のずれである。

### 長所4: CVE がゼロ

`npm audit` → **0 vulnerabilities** (出荷物・開発ツールとも)。

**反問: どうやってゼロにしたのか? ルールを緩めたのではないか?**

緩めていない。二段階で消した。まず**一度も import されていない実行時依存を
削除**し (下記)、次に**残った開発ツールの major 移行を検証付きで完了**した
(短所4 参照)。
`@xenova/transformers` は critical 1 + high 4 を背負っていたが、参照は
`vite.config.ts` の `optimizeDeps.exclude` 1行のみで、ビルド成果物にも
含まれていなかった (`grep -l xenova dist/js/*.js` → 該当なし)。
**機能の削除ではなく、機能が使っていない宣言の削除** (②削除する)。
副次的に `node_modules` が 128MB 減った。

## 第三問: 短所は何か? そして「なぜまだあるのか?」

### 短所1 (最大): CI が存在しない

`.github/workflows/` は**無い**。CI 定義は `docs/ci-workflow.yml` に
「GitHub App に workflows 権限が無いため push できなかった」という注記付きで
置かれているだけ。

**つまり `CLAUDE.md` が掲げる品質ゲートは、どこでも強制されていない。**

**反問: それは本当に「最大の」短所か? コードは動いているではないか?**

これが最大である理由は、**他のすべての欠陥の発生源**だから。本セッションで
発見したものを並べると:

| 発見 | CI があれば |
|---|---|
| `npm ci` が ERESOLVE で全停止 (lock 乖離) | 初回 push で検出 |
| E2E 23件中16件が失敗 | マージ前に検出 |
| CVE 16件 (critical 3) | 定期監査で検出 |
| bench の予算超過が exit 0 | ゲート自体の欠陥として検出 |
| a11y がオンボーディング画面しか見ていない | — (これは CI でも見抜けない。第四問参照) |

いずれも**長期間放置されていた**。人間のレビューは疲れるが CI は疲れない。

**次の一手 (⑤自動化する)**: 私は同じ権限制約で設置できない。
**推測ではなく実際に試して確認した** — workflow ファイルを含む push は
サーバー側で拒否される:

```
! [remote rejected] ... (refusing to allow a GitHub App to create or update
  workflow `.github/workflows/ci.yml` without `workflows` permission)
```

ユーザーの操作が要る:

```
mkdir -p .github/workflows && cp docs/ci-workflow.yml .github/workflows/ci.yml
```

これが**このプロダクトに残る単一で最大の改善**である。

### 短所2: 構築されるだけで一度も呼ばれないエンジンが11個

`app/main.ts` は 28 個のエンジンを `new` するが、メソッドが**一度も呼ばれない**
ものが 11 個ある (実測: `this.<name>.` の出現回数がゼロ):

```
ai  captions  collab  colorGrading  keyframes  motionGfx
multiCam  plugins  proxy  textEditor  video
```

**反問: 構築するだけなら害は無いのでは?**

害はある。①起動時に無駄なメモリと初期化コストを払う ②「ある」と誤認させる
(現に `@xenova/transformers` は CVE 5件を背負ったまま**無いのと同じ**だった)
③リファクタのたびに保守コストを取る。

**次の一手 (②削除する)**: 「配線するか、消すか」を engine ごとに1つずつ決める。
中間状態 (new するだけ) を残さない。CLAUDE.md の `future/` 隔離 (現状: 空) が
まさにこのための場所である。

### 短所3: lint 警告 293 件 — 本番コードの設計負債

内訳 (実測):

| ルール | 件数 |
|---|---|
| `no-non-null-assertion` | 161 |
| `max-params` (>4) | 75 |
| `complexity` (>15) | 35 |
| `max-depth` (>4) | 17 |
| `max-lines-per-function` (>200) | 5 |

ディレクトリ別: `render` 39 / `export` 30 / `scopes` 28 / `color` 26 / `ai` 26 /
`bench` 24 / `core` 23 / `undo` 17 / `audio` 17 / `app` 13。

**反問: 964 件あったはずでは? 数字を作ったのではないか?**

作っていない。**`tests/**` の `no-non-null-assertion` だけを除外した** (671件)。
このルールが守るのは「本番コードが null で落ちること」だが、テストでは null に
当たった時点で**そのテストが落ちる**のが正しい振る舞いであり、`!` は検証の省略
ではなく前提の宣言である。`?.` に書き換えると「null なら黙って通る」テストになり、
**かえって検証が弱くなる**。

除外の目的は数字を減らすことではなく、**残った警告に意味を持たせる**こと。
本番コード側の 293 件は**1件も消していない** — ルールを緩めて数字を作るのは偽装。

**次の一手 (③単純化する)**: `render/` の 39 件から着手。ただし
「動いているコードを警告のために触る」のは退行リスクを買う行為なので、
**その領域を機能変更で触るときに併せて直す**のが正しい順序。

### 短所4: devDependencies の CVE 6件 → **解消済み**

**反問: なぜ上げないのか? 面倒なだけでは?** と自問したうえで、実際に上げた。

以前**まさにそれで CI が全停止した**経緯 (Dependabot がロックだけを major へ
進め `npm ci` が ERESOLVE で失敗) があるため、**検証しながら**進めた:
vitest 2→4 / `@vitest/coverage-v8` 2→4 / vite 5→8 / esbuild 0.23→0.28 /
`@vitejs/plugin-react` 4→6 を一括更新し、全スイート + 実ブラウザ + build を通した。

結果 **`npm audit`: 0 vulnerabilities** (16 → 6 → **0**)。

移行で判明した実バグ (いずれも**元から誤りだった**もの):

- **`new` される global の差し替えをアロー関数で書いていた** (`tests/setup.ts` の
  `OffscreenCanvas` / `AudioContext` / `OfflineAudioContext` / 各 Observer、
  `integration.test.ts` の `VideoEncoder` / `VideoDecoder` / `AudioContext`、
  `plugin-manager.test.ts` の `Worker`)。アロー関数は `[[Construct]]` を持たない
  ため `new X()` は本来必ず落ちる。vitest 2 では素通りしていて表面化していな
  かっただけで、**120件超のテストがこの1つの誤りで落ちた**
- spy の呼び出し履歴がテスト間で引き継がれ、`project-manager` の1件が
  実行順に依存していた → `mockClear()` で独立させた
- Vite 8 (rolldown) は `manualChunks` を**関数形式のみ**受け付ける。
  `@vitejs/plugin-react` 6 は `babel` オプションを廃止したため、本番の
  console 除去を esbuild の `pure` へ移した (`drop: ['console']` を使わないのは
  **error/warn まで消える**ため — 障害時に何も出ないビルドは調査不能になる)

### 短所5: 書き出しは1トラック相当の合成しかできない

`export/timeline-render.ts` は重なりを `layer` 順に重ねて描くが、
**ブレンドモード (加算・乗算等) とトランジションが無い**。GIF プリセットは
`containerForPreset()` が `null` を返して明示的に失敗する (Mediabunny が GIF を
持たないため)。速度変更 (タイムリマップ) も未配線 — Inspector の速度スライダーは
**書き込み先が無いため削除した**。

**反問: それは「短所」か、それとも「未実装」か?**

区別は重要で、**ユーザーに嘘をつくかどうか**で分かれる。速度スライダーは
操作できるのに何も起きなかった = **嘘**だったので削除した。GIF は明示的に失敗
するので嘘ではない = 未実装。現在、書き出しが拒否するのは
「タイムラインが空」「素材がライブラリに無い」「映像トラックが無い」
「GIF」「このブラウザが扱えないコーデック」だけで、**実装漏れを理由に拒否する
経路はゼロ**になった。

## 第四問: ゲート自体は信用できるのか?

**答**: **できなかった。** 本セッションで3つのゲートに欠陥が見つかった。

### a11y ゲート: エディタを一度も監査していなかった

`tests/a11y.spec.ts` は `/` を開いて監査していたが、`/` は**初回起動のティア
選択画面**であり、ユーザーが大半の時間を過ごすエディタ本体 (メディアブラウザ /
プレビュー / タイムライン / ヘッダ) は**一度も監査されていなかった**。

エディタを監査対象に加えたところ、**critical 3件**が即座に出た:

1. `input[type=file]` にラベル無し — 実在の欠陥。修正 (11ロケールに
   `media.fileInputLabel` を追加)
2. 検索入力にラベル無し — `placeholder` は支援技術にとってラベルではない
   (入力すると消える)。`aria-label` を追加
3. `div` のコントラスト比 1.14:1 — **監査器側の誤検出**。ヘッダのバッジは
   cyan→blue グラデーション上の黒文字 (実測 約5.3:1 で AAA 大文字基準を満たす)
   だが、`findBackground()` が `backgroundColor` しか見ずグラデーションを
   **素通りして**暗いヘッダ色と比較していた

3 は監査器を直した (`accessibility/wcag-auditor.ts`)。背景画像を塗る要素に
当たったら `null` を返して**判定を飛ばす** — 併せて「どこにも塗りが無ければ白
(`[255,255,255]`) と仮定する」フォールバックも削除した (暗色テーマのアプリで
白背景を仮定した比率は事実と無関係)。

> **教訓**: 誤検出はゲートへの信頼を壊し、**結局ゲートごと無効化される**。
> 間違った比率は、比率が無いより悪い。

### bench ゲート: 3つの欠陥

1. **予算超過が exit code に影響しなかった** (`console.warn` のみ)。
   `effect.alpha_composite_1080p` が予算 18ms に対し 36.68ms (+103.8%) でも
   `Status: PASS` / exit 0
2. **1ms 未満のノイズを CRITICAL と報告**。コード変更ゼロの再実行で
   `0.00ms → 0.00ms (+100.3%)` が critical 判定。→ 絶対差 0.5ms 未満は
   判定対象外にした (60fps 予算 16.7ms に対する下限として)
3. **13本中5本がベースラインに無く、退行検出の外**にいた (警告のみ)

現在はこの3つの AND でゲート判定する。

さらに、ツールチェーン移行後にゲートが**5回中5回落ちる**ようになったため
掘り下げたところ、根本原因が判明した: 判定は mean と p95 の**悪いほう**を
同じしきい値で裁いていたが、**p95 は裾の統計量であり平均よりはるかにばらつく**。
同一コードのまま繰り返した実測:

| 指標 | 実測値の振れ |
|---|---|
| `gaussian_blur_720p` の平均 | 16.25 → 17.57ms (+8%) |
| 同 p95 | 16.73 → 19.75 → 22.10 → **26.81ms** (+60%) |

対処は2つ。**しきい値を単純に緩めるのは誤答**で、本物の退行まで見逃す:

1. **p95 のしきい値を平均の2倍に**する (判定から外しはしない —
   `bench/CLAUDE.md`「平均だけで判断しない」に従う。60fps では裾の遅さこそが
   体感を壊す)。分散が大きい分だけ広げる、という統計的な根拠に基づく
2. **critical は再現を要求する** — 疑わしい benchmark だけ測り直し、二度とも
   critical のときだけ退行と認める。単発のノイズは再現せず、本物は必ず再現する

結果: 無改変で **5回連続 PASS** (対処前は 0/4)。かつ `gaussian_blur_720p` に
意図的な2倍の処理を注入すると `[CRITICAL] +91.4%` → 再測定でも再現 → **FAILED**。
**安定性と感度の両方**を実測で確認している。

**反問: ゲートを直したのは自作自演ではないか? 通したいから緩めたのでは?**

その疑いは正しく持つべきで、だから**感度が落ちていないことを注入テストで
示した**。3つの初期修正は**すべて「通っていたものを落とすようにした」変更**で、
緩和方向はノイズ足切りと p95 しきい値の2つ。どちらも
「実時間で 0.5ms 動いていない/裾は本質的にばらつく」という物理的・統計的な
根拠を持ち、**本物の退行が埋もれるのを防ぐ**ためのものである。
